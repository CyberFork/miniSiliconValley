# ②立棍方案提示词交付规范

在主棍与相关子棍已由人确认、AI 已完成执行棍的对齐检查后使用。此时交付的是具体游戏的完整提示词，不是空模板或另一个继续收集策划的教练提示词。

## 一个连续的交付物

默认在一个可复制的 Markdown 文本块中给出全文，不使用表格；能写文件且用户需要时可保存为单个 Markdown 文件。下面是组织规范，不要把占位标题和说明原样当成最终答案：应填入这次对话已经整理确认的具体内容。

1. **给后续开发 AI 的指令**
   - 简明说明：你将依据下方已确认的立棍方案开发这个游戏；先检查实际工作区与可用能力，按执行棍和依赖逐步推进。不重新采访已经明确的设计。
   - 区分整款游戏愿景、本轮获准实施范围和未来保留设计。未来尚待定或未确认部分不可自行开工；范围之外的发布、付费、账号和权限操作没有自动授权。
   - 若上层要求冲突或需要改变玩法、范围、接口及验收，向人提出具体问题；正常实现选择、自测与局部修复由开发 AI 自主完成。
   - 标明这些是交付提示词里的③指令，生成提示词的本次会话没有进行③。
   - 区分“本次只生成②”和“后续开发本轮只做哪些功能”：前者是当前生成过程的边界，不能被误抄成后续开发 AI 永远不准写代码的项目约束。主棍中执行者的未来开发职责与本次整理职责应说明清楚，不制造互相矛盾的指令。
2. **具体项目的主棍全文**
   - 名称、版本、人的真实确认状态，加上完整六要素。
   - 玩法、关键数值、视觉要求、输入输出、范围和验收标准不能以“见原稿”“参考上文”代替。
3. **具体模块的子棍全文**
   - 每根带可辨认的编号／名称、版本、关联主棍、确认状态和本轮／未来标记。
   - 每根均有六要素；共同规则可在同一个提示词内明确引用，不能只写“同上”“上一版”或引用不可访问的聊天记录。
   - 后续模块保留已知设计与真正待定项，不要求它们全部可立即开发。
4. **AI 已自查的本轮执行棍**
   - 写明上层依据、具体任务与交付、输入与依赖、后续实施边界、未来检查的输入／预期结果／方法。
   - 细化到可检查的具体任务，不只是把每根子棍重命名。任务数量依实际复杂度决定。
   - 标明计划对齐结果和“未执行”。没有运行证据，不写“游戏已通过测试”。
5. **依赖顺序、整体检查与交接状态**
   - 按依赖给出后续开发顺序，包含至少一条适用的完整玩家路径与异常／边界检查安排。
   - 说明后续开发应保留失败证据、修复后重跑相同检查，不能改设计标准来制造通过；这些操作目前均未执行。
   - 列出尚需提供的素材或运行环境、未来待定项，以及哪些内容已经确认。不要凭空指定框架、工具、部署位置或运行结果。

## 交付前自查

- 另一个没有本次聊天记录的开发 AI，是否能仅凭这份②读懂要做的游戏、当前范围、分工、交接和检查标准？
- 原策划每项核心要求、可选拓展是否都有归属？是否偷偷改了因果关系、数值、角色或结局？
- 主棍、子棍是否各有六要素，所有引用是否指向提示词内唯一、明确且有效的版本？
- 执行棍是否覆盖对应子棍验收，是否包含实际可检查的任务而非口号？
- 是否把未经确认的建议、待定项或模拟学生回答冒充人的决定？
- 是否只完成了②？不能为展示“方案有用”而顺手写代码、建游戏、执行测试或部署。

有本轮关键缺口或必要人工确认未完成时，回到对应阶段补齐；若用户暂时停止，只给明确标为“待确认”的阶段草稿，不制造最终确认。
