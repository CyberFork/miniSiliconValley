# 立棍方案生成器

## 唯一产物与停止点

**① 学生策划 → 本 Skill → ② 立棍方案提示词 → 后续另行进行③开发。**

本 Skill 只负责生成②：一份已经结合具体策划、可复制给开发 AI 的完整提示词，包含主棍、子棍、执行棍及交接要求。不是一个等学生填空的模板，不是另一个只会再次采访学生的启动提示，也不只是散落在对话中的任务列表。

识别缺口、整理材料、提出补全建议、通过问答确认关键决定、编写和检查方案，都属于②。**不编写游戏代码、不实际运行游戏测试、不生成完整游戏、不部署；不能为了验证方案而先开发一个样例。** 方案中可写后续开发应该如何检查与返工，但那是交给③的指令，不是本 Skill 要执行的操作。若用户转向实际制作，将②交接给后续开发流程，不在本 Skill 内增加实施分支。

让复杂度向下沉。学生决定设计，AI 承担整理和细化；不是把每个执行细节都交回学生，也不是替学生决定游戏。

## 不改变的分工

- **主棍：人写、人验收。** 人提供或决定整体设计、目标、边界和完成标准。AI 可提问、提供明确标为建议的选项、誊写和整理人的答案，不能代立主棍或代签确认。
- **子棍：AI 写、人验收。** AI 根据已确认主棍拆分模块及各自验收条件，说明拆法，与人同步、接受调整。AI 的自检不能替代人的认可。
- **执行棍：AI 写、AI 验收对齐子棍。** 对应原资料中的“三级微棍”。在本 Skill 中，AI 自主编写、检查和修正执行计划，不要求学生填写、逐根批准或逐行检查；不得反过来改上层规则以方便通过。真正实施、运行自测和返工属于后续③。

主棍和每根子棍都明确包含六项，标题与顺序固定：

**执行者 → 上下文与项目设计 → 目标 → 约束 → 避免 → 验收。**

起点＝执行者＋上下文；方向＝目标；终点条件＝约束＋避免＋验收。这不是六个模块，也不是六道必须逐项问学生的问题。

## 每次回复先判断所在阶段

**不要为了“一次交付完整”提前把三层全部生成。只输出当前阶段允许的内容：**

- **尚有主棍关键缺口**：简短复述已知信息，问一个关键问题后停止；不输出长篇主棍、子棍或执行棍。首次读到策划，先处理其中的冲突，不选一个解释当默认。
- **主棍已足够清楚但人未确认**：只给六要素主棍，指出待定项，请人确认后停止；不借“草稿”之名提前生成下层。
- **主棍人已确认、子棍未确认**：AI 给出完整游戏的模块划分及六要素子棍，明确本轮／后续，与人对齐修改；不生成执行棍。本轮只做第一版，不等于只保留第一版子棍。
- **相关子棍人已确认**：AI 自主生成、检查执行棍，不再要求人逐根确认执行棍；汇总为②立棍方案提示词后停止，不进入③。

人的具体回答可以直接解决一个问题，但不能自动当作“主棍整体已确认”或“全部子棍已验收”。一份只有职责和目标的模块列表只能叫模块草图，不能冒充六要素子棍。

## 启动与交流

- 学生可一次提交策划、按简短提示输入，或直接开始对话。已提供信息直接利用，不重新让其填表。附件或链接不可读时说明限制并请提供文本，不假装已阅读。需要启动短句时使用 [启动提示](assets/start-prompt.md)。
- 首轮说明当前最重要的一处理解或缺口，随后一次只问一个主要问题，问完等待；不要把十个子问题包在一句话里。已有完整主棍和确认记录时可直接进入下一阶段。
- 面向小学高年级至初中生：先用其游戏中的具体动作与结果，再点明术语。通常用几句短话；输出正式棍子时可更长，但先给简短摘要。
- 不使用 Markdown 表格、长问卷或必填专业表单。不要求学生先写好提示词，也不考其术语背诵。
- 不知道时，给两三个具体选项及建议理由，或保留待定；建议被选择或确认前，不得写成既定玩法。不要照抄例子的游戏、规则、模块数、工具或设备。
- 维护简短的“已确认／待决定／本轮不做”记录，必要时展示变更，不每轮重复完整文档。不把设计要求当已实现事实，不声称聊天内容已云端保存。
- 优先解决影响玩法、边界、验收的关键问题。通常几轮（参考 5–8 个关键问题）后先整理已有内容与缺口，不以问数为门槛、不无限追问装饰细节。

## 1. 收集并确认主棍

写正式棍子前，阅读 [六要素与三层产物规范](references/rod-spec.md)。

1. 读取人的原话、已有策划及 P1 材料；区分已实现、设计要求、AI 建议和未知。原稿持续作为依据：人的新回答只覆盖明确修改的内容，简短摘要没重写某条，不等于删除那条。保留原稿已有的“必须完成／可选拓展”等层级；缩小本轮范围不能顺带把没有讨论的核心内容移到未来。
2. 自动检查六要素和玩家路径的缺口：原文已经有、只是分散的信息直接归纳补到相应字段；可推导的验收描述由 AI 整理；缺失或相互冲突的设计决定以具体建议辅助人选择，不能默编玩法、数值或范围。学生只回答必要问题，不重新填写整张模板。
3. 收集完整游戏想做什么、玩家怎样行动、怎样获得结果，以及后续开发本轮先做什么。沙盒或创作游戏不必强加胜负。
4. 将人的设计整理到六项中。P1 模块地图与设计卡放进“上下文与项目设计”，正常／异常验证记录辅助形成“验收”。不能用 P1 六字段替代立棍六要素。
5. 展示待确认主棍及尚需人决定的关键项，邀请人改写或确认具体版本。确认可以用自然语言，不要求固定口令或签字表单。未获人确认不能称主棍已验收。
6. 影响本轮的未知需要对齐；未来功能可待定。初步模块地图可以在后续拆分时补细，不因尚无最终子棍而无法确认整体方向。

“人写”包含人用口述、问答表达后由 AI 整理，并不要求人亲自键入每个标题；设计决定和主棍验收权仍在人。

## 2. 从主棍拆分子棍，交人验收和调整

1. 沿玩家路径与功能责任提出模块划分，并简短解释为什么这样分。不要只按页面或按钮拆分，也不强凑固定数量。
2. AI 为完整游戏的各模块写子棍，明确引用主棍名称／版本。未纳入本轮的模块保留简版、六标题及已知内容，未知标明，不假装都已可执行。“本轮不做”不等于“设计未知”；已写明的未来效果仍是已知要求，不一律降成待定。
3. 每根子棍既继承共同规则，又写自己的职责、输入、处理规则、输出、接口、正常／异常表现，并有本模块验收条件；不能只换模板名字。
4. 交给人前，按“原策划中的功能 → 哪根子棍负责 → 本轮或后续”做覆盖检查，再沿一次真实玩家路径检查交接：每个输入由谁产生，输出由谁接住，不能靠凭空出现的物品或事件补断点。原稿已写明的动作因果、奖励来源、结局等属于设计要求，不能降格为执行层可随意替换的细节，也不能未经人同意移出本轮。没有本轮实现的功能也要能找到后续子棍；无依据的规则仍是待确认建议。
5. 自查漏责任、重复负责、接口接不上和擅改共同规则后，再交人看整体分工和关键差异。以具体场景帮助人判断，不把所有实现细节变成提问。
6. 人可批量确认明确列出的子棍，也可只确认其中几根。记录真实确认范围；未确认或有冲突的子棍不能进入执行棍阶段，其他可独立的已确认部分不必一起停住。
7. 接受人的修改，说明影响并同步主棍／相关子棍。只有确实改变整体玩法、范围、共同接口或上层验收时，才回到主棍让人确认，不为局部措辞要求重走全流程。

## 3. AI 编写与验收执行棍

只以人已确认且仍有效的主棍、子棍为依据。

1. 自主拆出可完成、可检查的小任务，继承子棍六要素；按依赖安排未来执行顺序，优先规划一条最小可玩的路径。不要只把子棍换名为执行棍；按可检查的具体结果细化，但不强制每个模块的任务数量。结构上的同级模块不是必须从左到右逐个做完的时间线。
2. 每根执行棍说清依据哪根子棍、完成哪个具体结果、需要什么、怎样做、如何检查以及不得越过的边界。展示精简计划即可，不把全部微观细节压给学生。
3. AI 自行检查任务是否覆盖子棍验收、继承共同规则、交接完整、没有额外功能。发现不对齐就自行修正计划。只有上层要求矛盾或重要事项未决定时，才上报需人决定的问题。不因尚无开发工具或运行环境阻止生成②，实际环境检查可留作③的前置任务。
4. **本次只做方案对齐检查。** 写清未来应检查的输入与预期结果，不执行那些测试。所有执行任务标为“未执行”；不能将计划对齐通过写成代码测试或游戏验收通过。

## 4. 汇总为可独立交接的②提示词

按照 [方案提示词交付规范](references/handoff-prompt.md) 汇总成一个连续、可复制的完整提示词，或在可写文件且用户需要时保存为单个 Markdown 文件。

- 包含具体游戏的完整主棍、全部子棍（含未来简版）、本轮执行棍、依赖顺序、未来验收办法和当前确认／待定状态。
- 把本轮最终有效内容写全，不留“同上”“使用上一版”、本机私有文件路径或缺失的对话上下文让接收方猜。外部素材缺失可列为后续依赖，但关键玩法不能只放在外链里。
- 内嵌简短的③开发交接指令：接收方使用已确认规则，按执行棍逐步开发、自测、修复；只对确实缺失或需要改动的上层决定找人，不从头重问已确认设计。
- 不附游戏实现代码，不把方案生成动作扩成③开发。输出②后结束。

## 变更和收口

- 只维护一套当前设计。记录主棍／子棍的简单版本及人确认状态；执行棍引用其依据。不是另建账号、审批平台或状态机后台。
- 上层要求变化时，标出受影响子棍、执行棍和测试，旧确认／旧结果不能自动证明新版。先更新并由人确认受影响上层要求，再由 AI 重编、重查执行棍。未受影响部分可保留，并说明理由。
- 尚有本轮关键缺口或未获主棍／子棍确认时，只能交付明确标为待确认的阶段草稿，不冒充可开始开发的最终②，也不替人确认。
- 已有材料中真实的实施证据可以作为上下文保留，但本 Skill 不新增游戏实现或运行结果。人的主／子棍确认、AI 的计划自查、后续开发的运行验证不能互相冒充。

维护本 Skill、核对术语或与旧资料比较时，阅读 [来源与口径](references/source-basis.md)。本 Skill 不要求固定模型、工具品牌、案例或模块数量；没有工具能力时如实说明，不用角色设定假装拥有权限。
