# LIVE RUN 产品与体验主棍

状态：开发基线（后续 UI、API 适配器和测试必须共同遵守）
建立日期：2026-09-02
适用范围：`tools/live-run/` 本地真实课堂联测

## 1. 唯一主棍

> 同一份真实课堂状态，按角色分层呈现；任何重构只能增加清晰度，不能丢掉身份、私密手牌、个人 RP、个人资金、团队资金和成长反馈。

LIVE RUN 不是八张内容相似的监控看板。它是九个相互配合的视角：

- 1 个 `LIVE RUN SCRIPT`：课堂的唯一人工主控，负责执行、观察、验收和解锁。
- 4 个导师席：分别看到本专业的主持动作、观察点、兜底和系统门槛。
- 4 个学员席：分别看到自己的历史身份、私密信息、当下动作、队友交流任务、个人成长和团队结果。

所有视角必须来自同一个真实课堂 Run，不得以静态占位符伪装同步。

## 2. 不可退化能力

以下是回归红线，不允许为了“更简洁”而删除：

1. **角色代入**：学员看到自己在本章的历史/复合身份、公开目标和能力。
2. **私密信息差**：学员只在自己的窗口看到服务器随机发给自己的三张手牌；卡片标题、正文和分享提示完整可读。
3. **个人成长 HUD**：学员的个人 `RP` 与个人钱包 `C` 常驻可见；没有建房时显示 `—`，不能把未知伪装成 `0`。
4. **团队经济**：团队资金 `C` 与个人钱包分开显示、分别命名，不能混成一个“资金”。
5. **当前行动**：学员只看到此刻能执行的一件具体动作，不把 PDMO、API phase、节点门槛等后台概念压给学员。
6. **交流视角**：学员明确知道“我看到什么、我要告诉队友什么、我要从队友那里听什么”。
7. **完成反馈**：学员知道“做成是什么样”，并能看见本轮所得 RP、资金或作品状态的变化。
8. **导师交接**：同一小块只突出一名主导师，其余导师显示具体观察任务而非抢讲内容。
9. **人工闸门**：执行成功只能进入“待人工验收”，绝不自动进入下一块。
10. **九窗口关系**：8 个角色窗口固定为 2×4；第 9 个主控窗口独立存在，不占角色席。
11. **证据边界不用暗号**：学员可见处始终写全 `F 有来源｜R 课堂模拟｜G 我们猜的｜U 还不知道`；不允许只显示 `F／R／G／U`、`F-01` 或“标 R”让初中生自行猜含义。

## 3. 三种信息层级

### 3.1 学员层：具体、第一人称、现在就能做

优先级从上到下：

1. **我是谁**：身份名、公开目标、可使用的能力。
2. **我现在做什么**：一句动词开头的任务；在尚未发牌时只能提示准备，不能要求“检查三张卡”。
3. **只有我看到的**：三张私密手牌及每张卡的分享提示。
4. **我怎么和队友合作**：
   - 我要说：用自己的话讲哪条线索；
   - 我要问：听队友时追问什么；
   - 完成样子：一个可以当场核验的结果。
5. **我的成长**：个人 RP、个人钱包、刚刚为什么获得或没有获得奖励。
6. **我们的结果**：团队资金、当前作品和团队阶段；它是次级信息，不覆盖个人成长。

学员层不得常驻显示：`learnerPdmoCount`、`intel-network`、`dm-gate`、API 版本、情报节点数量、后台角色约束等开发术语。导师可在需要时解释方法名，学员先经历，再命名。

### 3.2 导师层：主持、观察、兜底、验收

导师席可显示抽象结构，但必须服务于主持：

- 当前是否轮到我主导；
- 本块逐句口播或观察任务；
- 应看哪名学员、哪项行为；
- 卡住时只给哪一级提示；
- 什么证据出现后可以建议主 DM 验收；
- RP、个人钱包、团队资金发生了什么变化。

### 3.3 主控层：完整剧本与事实状态

主控窗口是 Notebook 式唯一真相：

- 五个宏步骤与 13 个可执行块；
- 历史轨、现实轨、三种玩法和四导师交接；
- 每块口播、学员动作、系统动作、道具、证据门、兜底；
- `执行 → 8 席/现场观察 → 人工验收 → 解锁下一块`；
- 真实 API 状态、错误、重试和审计事件。

## 4. 五问学员视角模型

Google 完整战役的每个 B01—B13 块，以及饿了么五步平行世界战役的 B01—B13 块，都必须提供以下字段，缺一不可：

- `world`：我正处在哪个具体情境；不提前泄露历史答案。
- `private`：只有我能看到的身份/卡片/资源。
- `say`：我要向队友讲什么。
- `ask`：我要从队友那里听到或追问什么。
- `done`：导师能当场看见的完成结果。

其中 `private` 来自真实课堂 API，不能由前端编造；其余四项由课程脚本提供。

## 5. 经济与成长语义

- `RP（声望）`：个人成长和社交信用；必须绑定具体证据原因。
- `个人钱包 C`：属于学员个人，可用于个人道具或权限。
- `团队资金 C`：属于团队，用于调研、产品、市场、运营投入。
- 三者不得互相替代，也不得只剩团队资金。
- 显示顺序：学员页 `个人 RP → 个人钱包 → 团队资金`；导师页可先显示团队资金，但仍需能查看学员成长。
- B12 真实结算默认将本章可分利润的 `40%` 转入四个人钱包，余额留在团队资金；只记已完成订单的模拟收入和实际运营成本。
- 系统不代学员花个人钱包；个人道具购买与自愿回投必须保留为学员选择。

## 6. 真实数据映射

数据均来自每个账号自己的 `GET /api/classroom/rooms/:roomId` 结果：

- 身份：`myIdentity.name/publicGoal/ability/privateConcern`
- 私密手牌：`myCards[].title/body/sharePrompt/credibility/state`
- 个人 RP：`viewer.reputation`
- 个人钱包：`viewer.walletTenths`
- 解锁：`viewer.unlockIds`
- 团队资金与账本：`economy.teamTreasuryTenths` 及相关交易
- 当前历史情境：学习者安全版本的 `chapter.studentGuide`
- 挑战/压力：当前 `challenge` 中已经向学员公开的部分

控制台公开快照不得包含登录密码、Cookie、完整账号文件或未到揭晓时点的 DM 史实答案。

## 7. 状态文案契约

- `ready`：准备动作；尚未发牌时不显示“检查自己的三张卡”。
- `executing`：明确系统正在同步，禁止重复点击。
- `awaiting-acceptance`：显示真实内容和线下动作，提示等待现场完成，而不是只说“等待主控”。
- `error`：保留当前任务和已有数据，解释如何恢复，不清空成长数据。
- `completed`：显示本次个人成长、团队结果与下一步现实行动。

## 8. 视觉基线

- 保留原先深海军蓝、芥末黄、珊瑚红、青绿色的 Mission Control 风格。
- 席位窗口保持高信息密度、窄屏可读、无横向溢出。
- 不再替换为白色/米色通用卡片站点。
- 参考基线：`outputs/msv-classroom-runs/seat-view.html` 的深色席位语言。
- 本次可视回归基线：[`assets/learner-b01-private-growth.png`](assets/learner-b01-private-growth.png) 与 [`assets/controller-b01-awaiting.png`](assets/controller-b01-awaiting.png)。
- 允许改信息层级和具体文案，不允许未经确认重做视觉系统。

## 9. 防跷跷板实施顺序

后续修改必须按顺序完成，并在每一步跑回归：

1. 先扩充真实 API 的角色快照：身份、私密手牌、RP、个人钱包、团队资金。
2. 按所选课程为 Google B01—B13 或饿了么 B01—B13 固化五问学员文案。
3. 再将学员页改为学员专属信息架构；导师页保持主持视角。
4. 再接入 9 窗口与主控联动。
5. 最后跑 13 块真实 API 全程，并逐块检查 4 个学员窗口。

任何一步发现旧能力消失，先修回归，不继续叠加新界面。

## 10. 验收清单

- 4 个学员首屏都显示不同身份或不同私密手牌，而不是四张相同监控面板。
- B01 执行前显示准备；执行后每人恰好三张不同随机卡。
- 学员首屏常驻显示自己的 RP、个人钱包和团队资金，三者标签明确。
- 学员页不出现 PDMO/API/节点数等后台术语。
- 每块都能回答“五问”，且四名学员因私密信息和分工不同而有所差异。
- 导师页仍可看到主导/待命、专业观察和验收提示。
- 8 个席位无重叠覆盖完整 2×4；Window 菜单另有 `LIVE RUN SCRIPT`。
- 主控没有点击人工验收时，任何窗口都不进入下一块。
- Google 完整真实 API Run 后：4 导师、4 学员、12 张随机卡、学员无强制 PDMO、最终 `completed`。饿了么真实 API 五步战役也必须逐一通过 13 个手动闸门、4＋4 席位、12 张随机卡、最终 `completed`；新 v2 回执须待真实重跑后覆盖；旧回执仅作审计，不冒充新验收。
