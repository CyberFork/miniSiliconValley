# Mini Silicon Valley 课程包标准与实施 SOP

> **Legacy（T-085 已替代）**：旧文件 Registry 与 `/control/editor` 操作已退休。现行唯一写入口是 `/studio/editor/`，请使用 [Course Platform SOP](COURSE_PLATFORM_SOP.md)。下文只作历史审计。


版本：Course Package v1
适用：Google、饿了么以及后续所有 LIVE RUN 课程

## 1. 主棍：平台不再把课程写死在页面里

系统被拆成三个稳定层：

1. **课程引擎**：账号、4 导师＋4 学员席位、不重复随机发牌、RP/个人钱包/团队资金、按块执行、人工验收和课堂 API。引擎只执行规则，不内置课件卡牌正文。
2. **标准课程骨架**：一世界、两双轨、三玩法、四导师、五大步、十三小块、六分钟 Demo。
3. **课程 JSON**：Google、饿了么和新案例的具体历史、来源、五阶段卡组、口播、任务、道具、席位动作与验收证据。**一个 JSON 就是一套可移植课件的内容真值。**

上课时选择课程，控制器只加载对应的**已发布 JSON**。编辑课程不会修改引擎，也不会静默改变正在进行的正式 Run；Alpha 调试 Run 只在导师明确点击“全部刷新 Alpha”后才加载最新完整修订。

## 2. 标准结构

### 五个大步骤

- 第 1 步｜找真问题：B01—B03，产品导师主导。
- 第 2 步｜定真方案：B04—B05，产品导师交棒给开发导师。
- 第 3 步｜做真产品：B06—B08，开发导师主导。
- 第 4 步｜进真市场：B09—B10，市场导师主导。
- 第 5 步｜跑真运营：B11—B13，运营导师主导；B13 完成六分钟 Demo Day。

### 十三个小步骤

- B01 进入历史现场、确认 4＋4 席位、随机获得私密信息。
- B02 毛线式交换：把孤立信息讲给队友，追问来源和未知。
- B03 美式攻坚：在压力与反证中冻结一张真问题卡。
- B04 比较方案价值，不把第一个点子当答案。
- B05 裁剪为本轮做得出的唯一方案赌注。
- B06 做出目标用户可以操作的 V0。
- B07 让失败真实发生，收集可观察证据。
- B08 根据证据改出 V1，不凭喜好加功能。
- B09 锁定第一小群目标用户与十秒承诺。
- B10 完成一次真实渠道实验并记录拒绝。
- B11 跑通可重复交付的最小 SOP。
- B12 记录收入、成本、团队资金、个人钱包、RP 与反馈迭代。
- B13 用 360 秒发布完整闭环，并区分历史世界线与玩家平行世界线。

这是当前可执行课堂 API 的安全骨架。课程编辑器允许修改每块的教学内容，不允许破坏 ID、顺序、API 动作和人工验收状态机。

## 3. 每个小步骤必须写清的 8 件事

1. **历史学习轨 `historyTrack`**：当时的人能够知道什么；哪些有来源。
2. **现实实践轨 `realityTrack`**：学生今天的真实项目要完成什么。
3. **学员一句话 `studentPrompt`＋`learnerLens`**：初中生眼前只做一件具体事情。
4. **导师逐句口播 `mentorScript`**：可以直接照读，抽象原理留在导师侧。
5. **游戏机制 `gameModes`**：毛线取信息、美式攻坚、德式经营的组合。
6. **八席任务 `seatTasks`**：4 位导师按顺序出现，4 位学生不固定为 P/D/M/O。
7. **道具与系统 `props`＋`systemActions`**：线下拿什么，执行后八个窗口变化什么。
8. **人工验收与兜底 `evidenceGate`＋`fallback`**：亲眼看见什么才过关；卡住时问什么。

证据语言始终使用完整中文：**F 有来源｜R 课堂模拟｜G 我们猜的｜U 还不知道**。不可把 R/G 写成真实历史。

## 4. 五阶段卡组是课程 JSON 的一等公民

每门课固定包含 5 套 `decks`，分别在 B01、B04、B06、B09、B11 发牌。默认是 4 名学员每人 3 张，同轮 12 张不重复，不根据身份或 P/D/M/O 分牌。

每张卡必须包含：

- `id`：稳定 ID；Alpha 热刷新时用它保留学员原来的手牌位置。
- `boundary`：`F` / `R` / `G` / `U`。
- `title` / `body` / `sharePrompt`：学员可直接读懂的标题、具体线索和交给队友时要说的话。
- `sourceIds`：指向同一 JSON 中 `sources` 的稳定 ID。F 卡至少要有一个有效来源；R/G/U 可以留空。

课程校验会拒绝缺卡、重复 ID、错误发牌块、F 卡无来源、引用不存在的来源以及不足 12 张的卡组。Google 与饿了么内置 JSON 均已迁移为 5 套、60 张实际卡。

## 5. JSON 目录与版本

### 代码内置、随发布走

- `tools/live-run/live-run-script.json`：Google。
- `tools/live-run/live-run-script-eleme.json`：饿了么。
- `tools/live-run/courses/course.schema.json`：可供 IDE 使用的 JSON Schema。
- `tools/live-run/courses/course-template.json`：中性、完整、可复制的 5×13 模板。

### Hecate 持久课程库、部署不覆盖

- `~/Services/minisv/data/courses/drafts/<course-id>.json`：当前 Candidate（内部目录名为 `drafts`，不是第二套用户概念）。
- `~/Services/minisv/data/courses/published/<course-id>.json`：已发布覆盖或新课程。
- `~/Services/minisv/data/courses/history/<course-id>/rNNNN-*.json`：每次保存的不可变历史版本。

规则：

- Candidate 永远不会进入正式上课选课区。
- 发布后，新建或彻底重置 Run 会加载新版；正式 Run 不热切换。
- Alpha 可显式加载最新有效 Candidate 或 Released；加载失败保留上一个完整版本。
- 发布文件可覆盖同 ID 的内置课程，但内置原件仍可回退。
- 保存使用 `expectedRevision` 乐观锁；两个人同时改时，旧页面不能覆盖新修订。
- 课程 ID 只能使用小写英文、数字和连字符，创建后保持稳定。
- JSON 仅保存数据，禁止脚本、HTML 事件或可执行表达式。

## 6. 九视窗课程编辑器与 Alpha 调试 SOP

入口：`https://minisv.vip/control/editor/`，只允许管理员和导师账号。

### 默认九视窗编排

1. 打开一门课后，课程库自动收起；页面先显示当前 Course Package、当前大步、五大步 × B01—B13 时序轴、4 导师、4 学员和底部第 9 个中控。
2. 先看顶部版本链：`Working Copy → Candidate → Alpha Active → Released`。任何未保存修改都必须停在 Working Copy，不得伪装成 Alpha 已生效。
3. 点击时序轴任一 Block。八席和中控必须同时显示同一个 Block；可用上一块／下一块、只看警告和三档密度巡检全课。
4. 用“八席总览／只看导师／只看学员／单窗精编／双窗对照”检查角色视角。中控永远位于八席下方，可以折叠或调高，但不遮挡席位。
5. 用预览状态检查待执行、同步中、待验收、错误和完成画面；用可见 seed 重现不同 4×3 手牌。它们都只是投影，不会创建或推进真实 Run。
6. 点击虚线提示的课程名称、大步、Block、中控口播、席位任务或卡牌内容。弹窗必须显示唯一 Course Package 路径；输入时所有依赖该路径的窗口立即更新。
7. 点击“只读 · 模拟”的 RP、钱包、团队资金、进度或运行状态，只能看到来源解释，不能获得伪造的课程输入框。
8. 需要精确处理结构、全课程卡牌或原始数据时，再进入“高级结构／抽卡内容／JSON 源码”。它们与九视窗编辑的是同一份 Working Copy。
9. 可用撤销／重做；按 `Command/Ctrl + S` 或点击粘性“保存整门课程”，生成新的不可变 Candidate。保存不会自动刷新 Alpha。

### Alpha 验收与 Released 发布

1. Candidate 保存后，顶部 Alpha 单元只提示版本差异；当前 Run、执行位置、手牌、RP、钱包和团队资金都保持不变。
2. 从工作台明确打开独立 Alpha 测试房，并在 LIVE RUN 主控点击“全部刷新 Alpha”。只有这一动作才把最新 Candidate 加载到当前测试 Run。
3. 用真实中控按 B01—B13 逐块执行和人工验收。预览模式没有 `/api/control` 写入能力，不能替代这一步。
4. 回到编辑器确认 Alpha Active 与 Candidate 的完整 digest 一致，且 Alpha 状态为 `completed`。
5. 点击“发布正式课堂”。浏览器会附带当前 Alpha `runId`、完整 digest 和完成状态；服务端再次检查已保存 Candidate、请求内容、Alpha digest 和回执完全一致。
6. 发布生成 Released revision，但不会静默更换既有正式课堂的绑定版本。新建或明确重置的正式 Run 才采用新版。
7. 需要回退时打开版本历史。旧快照只会复制成一个新的 Candidate revision；旧历史不覆盖，Alpha 仍需重新明确加载和验收。

### 卡牌精编

- “抽卡内容”支持标题、正文、分享提示、稳定 ID 和来源全文搜索，以及步骤、F/R/G/U、来源、当前 Alpha 已发状态筛选。
- 九视窗中的随机手牌携带稳定卡牌 ID 与源路径。点击标题、正文或分享提示，修改的是 `decks.N.cards.M` 源卡，不是某次发牌副本。
- “当前 Alpha 手牌”只在导师后台显示 4×3 稳定 ID；点击 ID 可以反查同一源卡。
- F 卡至少关联一个有效来源；R 卡必须明确“课堂模拟／不是史实”。

### 创建新课

1. 点击课程库右上角 `＋`。
2. 选择 Google 或饿了么作为课堂素材底座，填写稳定课程 ID 和名称。
3. 系统创建完整 Candidate，不创建空壳，并保留全部 5×13 运行契约。
4. 在九视窗中从 B01 到 B13 替换真实内容；不要只改标题。
5. 检查五步、13 块、八席和五卡组，保存 Candidate，加载 Alpha，跑完整验收，再发布 Released。

### 直接编辑 JSON

- “JSON 源码”可格式化并应用完整 Course Package，仍然只更新浏览器 Working Copy。
- “导入 JSON”先由服务端校验；失败不写盘。“导出 JSON”生成 UTF-8、两空格缩进的规范文件。
- 命令行校验：

```bash
cd tools/live-run
python3 course.py --validate path/to/course.json
```

## 7. 课堂运行流程底座

`case.campaignId` 现在只决定真实课堂 API 使用哪套身份、阶段机、挑战、账本和历史揭晓流程。**学员在 Alpha 席位看到的五阶段手牌始终来自当前课程 JSON**，不再把 `campaignId` 当隐藏卡牌数据库。当前安装的流程底座：

- `google-1995-2004`
- `eleme-2008-find-problem`

新课程克隆后可以直接在 JSON/编辑器里替换来源、60 张卡和 13 块课程内容，不需要改 TypeScript campaign 文件。只有要新增全新的账本/挑战/历史揭晓机制时，才需要开发第三套运行流程底座。

## 8. 发布前验收

- JSON Schema 与服务端深度校验均通过。
- 5 个大步骤、13 个小步骤完整，顺序未变。
- 每块 8 个席位任务完整；学生没有固定 P/D/M/O。
- 每块至少一个玩法、一个具体学员动作、一个人工验收证据和一个兜底。
- 历史事实有来源边界；模拟、推测、未知没有冒充事实。
- 5 套卡组都有至少 12 张；编辑器模拟发牌显示 4×3 且 12 张不重复；F 卡有有效来源。
- 学员文案可以由初中生直接执行，抽象概念只出现在导师侧。
- B01 随机发牌；B12 可见 RP、个人钱包、团队资金；B13 为连续 360 秒 Demo。
- Working Copy、Candidate、exact-digest 验收、Released、版本冲突、导入导出和新 Run 加载均测试通过。
- Alpha 热刷新后 Run ID/真实进度/账本/手牌位置保留，卡牌正文更新；8 席修订号、摘要和刷新序号一致。
- 无效更新不替换活动课程；回看不产生副作用；正式课堂不会因为编辑器保存而静默更新。
