## 这份目录解决什么问题

当前课程采用一世界、两条双轨；本页以下“六步”均为历史旧版资料，不能当作当前课程定义。早期资料曾记录两条互相正交的学习轴：

```text
1 → ∞  历史世界：时代、企业、人物、技术、事件如何持续演化
0 → 1  项目主线：一个真实项目如何从问题走到 Demo Day
```

下列内容记录早期对第二条轴的组织设想，供内部资料追溯；线上“课程大纲”以固定 chj 页面自身内容为准。

## 两种目录视图

### 历史旧版六步：纵向视图（默认）

一次只聚焦一种项目能力，跨企业归集相关案例。例如在“MVP 原型 + VC”中同时查看 YouTube、Google 与 Y Combinator。

每一步固定展示：

1. 核心问题
2. 学习目标
3. 学员行动
4. 交付物
5. 完成门槛
6. 历史案例与原始史实入口
7. 可进入的历史战役

### 企业全流程

沿一家公司或一个产品横向走完历史旧版六步。首个完整样例是 Google 搜索（1997—2000）。

企业当年未必使用“旧版六步”术语，因此每个节点必须标明：

- **直接案例**：史实本身直接对应本阶段的动作或机制。
- **课程映射**：教师为了学习迁移进行的重组或类比，不得写成公司的历史原话。

## 历史旧版六步（已被当前语义替代）

### 01 找问题

- 核心：先记录真实场景和问题信号，不夹带方案。
- 关键产物：问题信号清单、场景记录、利益相关者地图。
- 门槛：至少 3 个来自真实人的独立信号，写清人物、情境、行为和后果。

### 02 识别真问题

- 核心：验证频率、痛感、替代行为和改变意愿。
- 关键产物：访谈纪要、证据矩阵、目标用户画像、真问题陈述。
- 门槛：至少 3 位目标用户的一手证据，并写清停止该方向的反证条件。

### 03 想解决方案

- 核心：并行生成多条路径，再让证据决定取舍。
- 关键产物：方案对比卡、价值主张、用户旅程、风险测试卡。
- 门槛：至少比较 3 个方向，选定方案直接回应已验证问题。

### 04 MVP 原型 + VC

- 核心：做出端到端最小闭环，并用证据争取下一轮资源。
- 关键产物：MVP 范围、可运行原型、测试记录、资源预算、90 秒资源陈述。
- 门槛：真实用户能完成一个核心任务；资源请求有用途、里程碑和替代路径。
- 边界：VC 指人才、时间、算力、渠道与资金等资源论证，融资不是创业终点。

### 05 运营 + 品牌

- 核心：让真实用户进来、回来，并让品牌承诺被体验兑现。
- 关键产物：发布页、渠道实验、用户反馈、核心指标、品牌承诺、V2 差异。
- 门槛：至少完成一次真实使用、一次渠道实验和一轮反馈迭代。

### 06 Demo Day

- 核心：发布真实产品，展示完整证据链并承诺下一步。
- 关键产物：产品链接、现场 Demo、证据链路图、一页说明、复盘与下一步。
- 门槛：演示真实产品而非假界面，能回答问题证据、取舍、反馈和下一步。

## 历史旧版资料与当前语义

```text
历史旧版六步（课程大纲）
找问题 → 识别真问题 → 想解决方案 → MVP+VC → 运营+品牌 → Demo Day

关卡六幕（单场历史 RPG）
入场 → 调查 → 决策 → 平行反馈 → 史实对照 → 带回现实
```

上述旧版六步曾描述一支团队数天或数周的 0→1 过程。关卡六幕描述一节历史情境课内部的学习循环。两者可以嵌套，但不能互相替代。

## 同事如何新增内容

### 前置条件

- 已确认内容归属历史旧版六步中的哪一步。
- 涉及历史事实时，已在 `app/data/history.ts` 中建立带来源的事件。
- 已区分史实陈述与教学映射。

### 新增一个纵向案例

编辑 `app/data/curriculum.ts` 中对应阶段的 `examples`：

```ts
{
  id: "example-company-topic",
  organization: "Company",
  label: "这一案例训练什么",
  yearLabel: "YYYY",
  eventIds: ["evt-existing-source-backed-event"],
  missionId: "m-existing-mission", // 可选
  mappingKind: "direct", // 或 "course-analogy"
  teachingUse: "DM 如何用该事实训练本阶段能力。",
}
```

每个阶段至少保留 3 个案例。不要在课程文件里复制一段没有来源的“公司故事”；事实由 `eventIds` 关联并在界面实时读取。

### 新增一条企业全流程

在 `companyJourneys` 中新增公司，并按固定顺序提供六个 `steps`：

```text
find-problem
validate-problem
design-solution
mvp-vc
operate-brand
demo-day
```

每一步必须至少关联一个史实事件。若公司没有字面意义上的 Demo Day，应设为 `course-analogy` 并明确说明映射边界，不能伪造发布会。

### 八项归集字段

新增内容必须回答：

1. `stageId`：归属阶段
2. `claimType`：直接案例或课程映射
3. `eventIds`：史实锚点
4. `learningGoal`：可观察的学习变化
5. `action`：学员实际行动
6. `artifact`：可保存、可复核的交付物
7. `completionGate`：可判断的完成门槛
8. `dmPrompt`：追问证据、取舍或边界的问题

## 验证

完成编辑后运行：

```bash
npm run validate:data
npm test
```

预期结果：课程阶段、案例、企业流程、史实事件和战役外键全部通过，且界面交互契约没有回归。

## 常见错误

- **把好点子当问题**：回到人物、情境、行为和后果。
- **把课程类比写成史实**：改为“课程映射”，并写明企业当时没有采用该术语。
- **只有阅读材料，没有学生行动**：补充调查、制作、测试、协商或演示任务。
- **交付物无法验收**：增加数量、行为、质量或真实用户标准。
- **把融资或 Demo Day 当终点**：必须说明资源用途、真实使用证据和下一步判断。
