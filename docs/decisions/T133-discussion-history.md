## 2. 与 P1／T-132 的衔接

P1 的三项产出继续保留：

1. 自己游戏的模块地图。
2. 一个关键模块的详细设计卡。
3. 一次正常流程和一次异常流程的验证记录。

它们的共同作用是帮助学生**描述清楚模块，并检查描述是否足够明确**，而非要求在 P1 完成整款游戏或学习智能体开发。

P2 直接接住这些材料：

- 模块地图成为整体项目结构及协作关系。
- 设计卡成为提示词中相应模块的职责、规则和接口说明。
- 验证记录成为验收依据；已走查的结果与尚待程序验证的用例明确区分。
- 不把多个模块说明简单拼接成超长文本：还需说清共同玩家路径、跨模块数据／状态交接、统一规则及本轮范围。
- 允许引用或附上现有设计卡，不要求重新录入；有矛盾时修正原设计依据并保持一致。

开发顺序上先对齐 T-132 的模块描述与三项成果结构，再细化 P2 脚本和模板；不要求为了讨论 P2 而先完成 P1 的生产发布。

## 3. 五组完整立棍提示词结构

这五组是学生描述任务与控制标准的框架，不冒充通用 Agent 软件架构，也不与旧提纲里尚待命名的“五步操作法”混淆。

### ① 执行者定义

- AI 在项目中承担什么职责、协助谁。
- 可以使用哪些现有工具和操作权限。
- 哪些判断需要交给人，遇到什么问题应停止并询问。
- 不把角色设定当成真实能力或权限的来源。

### ② 上下文与项目设计

- 游戏是什么、给谁玩、核心体验是什么。
- 当前已有材料、实现状态、设备和资源条件。
- 已确认事实、设计选择、猜测与未知分别是什么。
- 玩家核心路径、模块地图、各模块详细描述及连接关系。
- **这里主要承接 P1 的成果**，保留职责、输入、处理、输出、接口、正常／异常分支。
- 区分“设计要求”与“已经实现的事实”，不得把期望状态写成当前状态。

### ③ 目标

- 整体最终要为玩家带来什么结果。
- 本轮实现哪些模块、完成哪条玩家路径，交付什么。
- 不以“写了代码”“页面存在”“用了 AI”代替用户结果。
- 完整描述整体，不等于要求一次性实现所有模块。

### ④ 约束与避免

保留同一组中的两个明确栏目：

- **约束**：必须遵守的体验、技术、设备、时间、资源、隐私等条件。
- **避免**：不能出现的结果、不能采用的捷径、不能擅自变更的职责与接口。

示例：不能通过删除或跳过测试来宣称通过，不能修改无关模块以掩盖当前模块问题，不能把真实密钥或学员个人资料放入公开提示词。

### ⑤ 验收

- 各模块的正常、异常及必要边界行为。
- 模块连接后的端到端玩家路径。
- 需要交付的实际结果、测试证据与未完成项。
- 谁确认通过，存在冲突或证据不足时怎样报告和修正。
- 区分设计走查、AI 推测和真实程序运行；不能伪造“测试通过”。

## 4. 保留立棍原稿的整体思想

- 立棍贯穿任务始终，用方向、边界、验收及纠偏控制复杂度，不只是漂亮的提示词格式。
- 原稿“起点区域／目标／终点区域”继续保留为解释框架：起点对应执行者与上下文；目标对应目标；终点对应约束／避免与验收。
- 原 P2 七格模板中的“避免／约束”合并分组但不丢内容；“方式”放到执行流程说明，不另创与五组冲突的模板。
- **主棍把整体说完整，子棍限定本轮的模块任务。** 子棍必须继承主棍的共同边界与总体验收，不能各自做对却无法组合。
- 主棍由人确认；AI 可以派生子棍及其验收，人检查对齐；微棍可在授权范围内拆解、执行、自检和返工，异常需要上报。
- 保留注意力杠杆：人关注关键方向、边界、证据和异常，不要求控制每一个执行细节，也不能将最终责任交给 AI 自我声明。

## 5. Agent 等技术内容的从属位置

课程中心始终是**描述并使用完整项目立棍提示词**。以下内容用短演示解释机制，不各自发展为主任务：

- 提示词与上下文：说明为什么需要完整交代任务及设计依据。
- 结构化表达：区分方便人和模型阅读的标题／字段，与供程序处理的工具参数格式。
- 工具调用：模型提出请求，运行系统执行并返回结果；“说已经做了”不等于外部操作真实发生。
- MCP：标准化连接外部能力与资料的一种协议，不等于模型、不等于 Agent，也不是所有工具调用必需的前置阶段。
- Agent 与工作流：说明任务如何被组织、执行、反馈和停止；不把工作流简单定义为某个框架的简化版。
- RAG：在需要额外资料时检索相关内容并作为回答／执行依据；不要求每个项目都使用，也不保证检索结果或生成结果必然正确。
- 记忆、Skills、SubAgent 仅按理解需要安排教师补充，不强制学生安装框架、接入服务或学习整套开发协议。
- 提示词中的限制不能替代真实系统权限；课堂演示仅使用授权的材料、工具和测试环境。

不得使用“提示词→MCP→Agent→RAG”作为所有系统必须经过的技术升级路线。可以作为逐步理解能力的教学顺序，但它们承担不同职责。

## 6. 建议教学活动与最终成果

以下活动顺序是实施建议，具体页数、时长与现场执行程度仍需对齐：

1. 从 P1 的同一游戏及模块卡开始，比较只提供一句模糊要求与提供完整设计依据的差异。
2. 识别只描述单个模块时缺失的整体目标、协作关系与统一边界。
3. 按五组框架组织项目主棍提示词，引用 P1 材料而非重做。
4. 交换给同伴或 AI 复述，检查是否理解为同一个游戏、同一条路径和同一实施范围。
5. 选择关键模块形成本轮子棍，确认其继承主棍、接口和验收要求。
6. 视课堂条件做受控执行或明确标注的纸面演练；依据实际证据修正提示词及设计描述。

**核心最终成果：一份包含 P1 模块设计的完整项目立棍提示词。**

子棍和验收反馈作为对这份主棍的验证材料，不把课程拆成多个无关作品，不以完成一个独立 Agent 或 NPC 作为通过标准。
