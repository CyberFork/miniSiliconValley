# 完善 Alpha 实际课程编辑器的卡组编辑、学员预览与同步验收

## 原始记录

我看当前课件编辑器中的 JSON 内容还是缺少之前已经看到过的抽卡具体内容，例如“创始成员亲自送餐”“电话和餐厅信息是早期入口”“多张订单需要排路线”。为什么之前 Alpha 测试课可以看到这些私密卡，但是当前课程编辑器看不见？是否还没有做完？

补充确认：`/workshop/` 是团队早期讨论课程如何搭建时使用的课程共识工具。当前课程框架和基本雏形已经形成，后续主要通过 Alpha 实现和验证；本任务的重点是完善 Alpha 的实际课程编辑器。

## 产品范围重新确认

### 本任务主线

- 实际课程编辑器：`https://minisv.vip/control/editor/`
- 实际课程主控：`https://minisv.vip/control/`
- 实际测试环境：Alpha 的 4 个导师席位＋4 个学员席位。
- 实际内容真值：Alpha 运行课件 JSON，即 `sources`、`decks`、`macroSteps`、`blocks` 和运行规则。

### 已确认的实施决策

- 编辑器采用三个一级工作区：**课程结构／抽卡内容／JSON 源码**；“抽卡内容”不再埋在步骤表单内部。
- 内置 Google 与饿了么基线均严格为 5 组／60 张；后续团队课件允许每组多于 12 张，因此发布门槛是“恰好 5 组且每组至少 12 张”，而不是错误地禁止扩充到 60 张以上。
- 不新增 `internalOrder`，也不批量迁移既有 60 张饿了么卡：稳定 `id` 已承担运行身份，作者标题可保留旧前缀；学员显示标题由唯一共享渲染器派生，避免第二套字段漂移。
- “未读／已读／已讲出”属于预览或 Run 状态，绝不写回课程 JSON。
- 历史恢复采取 **append-only**：选择旧快照时生成一个新的草稿 revision，不覆盖旧历史，也不自动刷新 Alpha。
- 变更型端到端测试在隔离课程仓库和隔离 Run 中完成；生产只做登录后的只读浏览器/API 核验，避免把自动化测试文字写入正在使用的课程或课堂。

### `/workshop/` 的定位

- `/workshop/` 是历史阶段的课程共识与讨论工具，不是 Alpha 运行课件编辑器。
- 不要求把 `/workshop/` 的工坊 JSON 与运行课件 JSON 合并。
- 不在本任务中继续扩展其故事幕、会议决策或本地存储能力。
- 可以在后续站点整理时将其标记为“早期课程共识工坊／历史工具”，但这不是 T-074 的核心交付。

## 调研结论

### 1. 卡牌底层数据没有丢失

当前本地和生产的饿了么运行课件均包含：

- 5 个阶段卡组；
- 每组 12 张卡；
- 共 60 张卡；
- 每个阶段为 4 名学员各发 3 张，同轮不重复。

当前 Alpha 快照 `active-course.json` 也包含相同的 5 个卡组和 60 张卡。因此“Alpha 能看到卡”不是系统临时生成了课件 JSON 之外的内容。

### 2. 用户指出的三张卡已经在运行课件 JSON 中

它们都位于第一步“找真问题”的 `decks[macroStepId=find].cards`：

- `e08-c-05`：创始成员亲自送餐，`boundary=F`，有两个来源 ID。
- `e08-f-02`：电话和餐厅信息是早期入口，`boundary=F`，有来源 ID。
- `e08-r-04`：多张订单需要排路线，`boundary=R`，明确是课堂模拟，不配置史实来源。

对应文件：

- `tools/live-run/live-run-script-eleme.json`
- 生产 `~/Services/minisv/current/live-run/live-run-script-eleme.json`
- 当前 Alpha `~/Services/minisv/data/controller/active-course.json`

### 3. 学员看到的完整卡片是运行时组合结果

学员端的“私密卡 1 · F 有来源 · 可查来源 · 未读”不是 JSON 中一整条固定字符串，而是由以下字段和状态组成：

- `私密卡 1／2／3`：该卡在本名学员随机手牌中的位置。
- `F 有来源／R 课堂模拟`：卡牌 `boundary`。
- `可查来源／不是史实`：证据边界说明映射。
- `未读／已读／已向团队讲出`：当前 Run 中当前学员的动态状态。
- 标题：来自 `title`，学员端会去掉 `F-02 ·`、`C-05 ·` 等内部前缀。
- 正文：来自 `body`。
- 交给队友时说什么：来自 `sharePrompt`。
- 来源编号：来自 `sourceIds`。

所以，“未读”“私密卡 1”不应被写死到课程 JSON；但 Alpha 课程编辑器应能用相同渲染规则预览学员最终看到的完整卡片。

### 4. `/control/editor/` 当前生产加载链路没有丢掉 `decks`

针对用户确认的实际地址重新核验后，当前生产状态如下：

- `/control/editor/` 返回的当前版 HTML 已包含“阶段卡组”“新增卡”“模拟 4 人发牌”和“JSON 源码”控件。
- 编辑器成功请求 `/control/api/courses/eleme-2008-find-problem?variant=draft`，响应是完整运行课件，而不是只有课程元数据。
- 服务端用与生产 API 相同的 `CourseRepository.load(..., variant="draft")` 读取饿了么课程，确认顶层存在 `decks`，数量为 5，卡牌总数为 60。
- `editor.js` 的 `syncRaw()` 对整个课程对象执行 `JSON.stringify(course, null, 2)`；正常情况下，“JSON 源码”页签中必须包含顶层 `"decks": [...]`。
- 静态编辑器和 API 都发送 `Cache-Control: no-store`，当前实现并不应长期缓存旧 JSON。

因此，目前不能再把问题描述为“后端没有把卡牌交给 `/control/editor/`”。更准确的判断是：**卡牌已经到达实际编辑器，但现有界面没有把“抽卡内容编辑”设计成足够明确、可发现、可从学员文案反查的一级能力**。如果某次实际页面连 `decks` 都没有，则属于异常加载／版本完整性故障，编辑器当前又没有明显报错来阻止这种误导状态。

### 5. 当前编辑器中理论上的查找位置

- 结构化编辑：课程基本信息下方 → 五步骤页签 → `STAGE DECK · JSON 真值／阶段卡组`。
- 原始 JSON：切换“JSON 源码” → 搜索顶层 `"decks"`、卡牌 ID `e08-c-05` 或标题“创始成员亲自送餐”。
- 当前只能查看所选步骤的一组卡；没有跨五步的全局“抽卡内容”入口和搜索框。

这也是本 Todo 要解决的核心：不再要求课程编辑人员知道内部 JSON 路径或卡牌 ID，打开编辑器就应能明确看到“抽卡内容”，并能用学员实际看到的句子定位和编辑。

## 原始缺口与完成结果

底层卡组 Schema 和 Alpha 发牌本来已经存在；T-074 已将以下缺口全部收口到真实课程编辑器、共享学员渲染器、版本 API 和自动化验收中。

### A. 卡牌内容不容易被找到

**完成：**已增加“抽卡内容”一级工作区、跨五步全文搜索、五类筛选与稳定 ID 反查。

- 编辑器按当前五步展示卡组，但没有全课程卡牌搜索。
- 没有按步骤、F／R／G／U、来源状态筛选。
- 用户拿着学员窗口中的一句话，无法快速反查对应卡牌 ID。
- 60 张卡混在五个卡组中，仅靠切换步骤和滚动寻找，容易误判为 JSON 没有内容。
- 页面没有名为“抽卡内容”的一级导航；实际区域叫“阶段卡组”，与 Alpha 学员端“私密卡”的名称缺少直接对应。

### B. 编辑字段与学员最终显示不一致

**完成：**已抽取 `card-view.js` 作为编辑器与 Alpha 学员席的唯一共享渲染器，并补齐 F/R/G/U、状态、标题清理、来源与 HTML 转义。

- 编辑器显示内部标题，学员端会清理内部前缀。
- 编辑器没有复用 `seat.js` 的证据标签、标题清理和易读文本转换。
- 编辑人员看不到“私密卡 N／F 有来源／可查来源／未读”组合后的实际效果。
- `e08-c-05` 的内部标题前缀是 `C-05`，但证据边界为 F；编辑端容易误解，学员端则隐藏该前缀。

### C. 课程版本和数据来源不够显眼

**完成：**顶部已同时显示 release/build、Schema、5/13/卡组与卡数、来源、revision、digest 和 Alpha refresh epoch；不完整包或版本不一致会阻止发布。

- 需要更明确地展示当前正在编辑的是哪一门课程、内置基线／草稿／已发布版本、revision 和 digest。
- 需要同时显示编辑器最新版本与 Alpha 当前运行版本。
- 若用户加载到旧浏览器资源、旧草稿或错误课程，当前界面缺少足够明显的诊断提示。
- 当前生产课程库没有用户持久化的草稿／发布副本，主要读取内置课程；这一状态也应在界面明确标识。
- 如果前端没有渲染阶段卡组或原始 JSON 缺少 `decks`，编辑器不会在页面顶部立即显示“课程包不完整／界面版本不匹配”的阻断错误。

### D. 缺少“编辑卡牌→刷新 Alpha→学员看到变化”的完整验收

**完成：**已在隔离课程仓库与隔离 Run 跑通变更型闭环；生产只做登录后的搜索、预览、手牌、版本与布局只读验收，写操作为 0。

- 现有测试分别证明了卡组、模拟发牌、版本刷新和八席同步，但没有把用户指出的具体卡作为一条完整验收链。
- 没有在生产环境中从编辑器搜索卡牌、修改、保存草稿、刷新原 Run，再到指定学员窗口确认新内容。
- 因此实现已经有主体能力，但尚未以课程编辑人员能够直接确认的方式闭环。

## 目标形态

### 1. Alpha 课程编辑器成为唯一制课工作台

- 从 `/control/` 一键进入 `/control/editor/`。
- 编辑器只处理真正可以运行的课程 JSON。
- 页面持续显示课程 ID、课程名称、案例、课程类型、版本、digest、5 个卡组和卡牌总数。
- 当前 Alpha Run 使用的课程和编辑器当前课程不一致时，显示强提示，不允许用户误以为修改已进入当前 Run。

### 2. 增加完整卡牌库

- 增加“卡牌库”一级区域，而不只是在每个步骤内部显示卡组。
- 支持搜索：标题、正文、`sharePrompt`、稳定 ID、来源 ID。
- 支持筛选：五步骤、F／R／G／U、是否有来源、是否被当前 Alpha 手牌使用。
- 搜索结果显示卡牌 ID、所属步骤、抽卡区块、证据边界和来源数量。
- 点击结果直接跳转到对应步骤和编辑表单。
- 页面顶部显示实际卡组／卡牌数量；内置基线应为 `5 个卡组 / 60 张卡`。不是 5 组或任一组少于 12 张时禁止发布并给出具体缺口；允许后续课程在每组 12 张以上扩充。

### 3. 增加与学员席位一致的卡片预览

- 每张卡同时显示“编辑字段”和“学员最终效果”。
- 预览复用 Alpha 学员席位的标题清理、边界标签和易读转换规则，禁止复制两套容易漂移的逻辑。
- 预览可切换状态：未读、已读、已向团队讲出；这些只用于预览，不写回课程 JSON。
- F 卡显示实际来源编号和来源详情；缺少来源时阻止通过校验。
- R 卡明确显示“课堂模拟／不是史实”。
- 显示内部稳定 ID，但学员预览不暴露内部编号。

### 4. 显示当前 Alpha 手牌映射

- 导师／管理员可在编辑器查看当前 Alpha 每个学员在当前步骤抽到的 3 个卡牌 ID。
- 点击某个手牌 ID 可直接打开该卡的编辑与预览。
- 只显示当前内部测试 Run；不得把学员私密手牌开放到公开页面。
- 明确“已发手牌保存的是稳定卡牌 ID”，刷新课程后仍按相同 ID 对应更新内容。

### 5. 加强课程版本与缓存诊断

- 显示：编辑器资源 release、课程来源、草稿 revision、发布 revision、Alpha active revision、digest、refresh epoch。
- 如果前端资源版本落后于服务端课程 Schema，提示强制刷新，而不是静默隐藏字段。
- API 返回课程时同时返回 `deckCount`、`cardCount`、Schema 版本和 digest，前端加载后校验。
- 原始 JSON 没有 `decks`、不是 5 组或少于每组 12 张时，显示阻断错误，不能呈现为一个看似正常的课程。

### 6. 保持 Alpha 显式同步边界

- 保存草稿不会自动修改正在运行的 Alpha。
- 点击“全部刷新 Alpha”后才把完整新版本载入原 Run。
- 刷新保留 Run ID、执行位置、课堂成员、提交、评分、RP、个人钱包和团队资金。
- 已发手牌继续使用稳定卡牌 ID；相同 ID 的正文修改应在刷新后进入对应学员视图。
- 正式课堂绝不能因为 Alpha 编辑器保存草稿而静默更新。

## 数据模型整理

T-074 采用现有 Course Package v1 卡牌结构，不引入第二套显示标题或内部序号：

```json
{
  "id": "e08-c-05",
  "boundary": "F",
  "title": "C-05 · 创始成员亲自送餐",
  "body": "历史行动……",
  "sharePrompt": "说出亲自送餐能看到的一条证据……",
  "sourceIds": ["src-eleme-sjtu-youth-origin"],
  "credibility": "high"
}
```

明确规则：

- `id` 是发牌、热刷新、手牌反查和历史 Run 对应的唯一稳定身份。
- `title` 是作者字段；共享渲染器在学员侧清理 `F-02 ·`、`R-04 ·`、`C-05 ·` 等旧前缀。
- `boundary` 是证据边界唯一真值；不得从标题中的 `C/F/R/G/U` 猜测并覆盖它。
- `未读／已读／已向团队讲出` 只属于 Run/预览状态。
- 旧 JSON 无需迁移，已发手牌 ID 不会因界面完善而失效。

3. 抽取并复用学员卡片渲染规则，实现同款预览。
4. 增加当前 Alpha 手牌 ID 到卡牌编辑器的反向定位。
5. 增加不可变历史列表，并把旧快照恢复为新的草稿 revision。
6. 完成指定三张卡的隔离端到端同步验收与生产只读验收。

## 核心验收场景

### 场景 1：找到三张指定卡

1. 进入 `/control/editor/`，选择“饿了么｜五步创业闭环”。
2. 页面显示 `5 卡组 / 60 张卡`。
3. 搜索“亲自送餐”，定位 `e08-c-05`。
4. 搜索“电话和餐厅信息”，定位 `e08-f-02`。
5. 搜索“排路线”，定位 `e08-r-04`。
6. 三张卡的 boundary、正文、分享提示和来源关系均正确。

### 场景 2：预览学员实际所见

1. 打开 `e08-c-05`。
2. 编辑区显示稳定 ID、F、正文、提示和来源。
3. 学员预览显示“私密卡 N · F 有来源 · 可查来源 · 未读”。
4. 预览标题不显示内部 `C-05 ·`。
5. 切换到 `e08-r-04` 时明确显示“R 课堂模拟 · 不是史实”。

### 场景 3：修改并同步原 Alpha Run

1. 修改目标卡的 `body` 或 `sharePrompt`。
2. 保存草稿，编辑器显示新 revision 和 digest。
3. Alpha 主控显示“有新版本待刷新”，但当前 Run 不自动变化。
4. 点击“全部刷新 Alpha”。
5. 8 个席位显示同一 revision、digest 和 refresh epoch。
6. 已抽到该稳定 ID 的学员看到更新后的卡牌；其他手牌分配不漂移。
7. 回滚到上一完整版本后，卡牌和八席状态恢复一致。

## 自动化验收标准

- 课程 API、编辑器 JSON 和 Alpha `active-course.json` 对同一 revision 的 digest 一致。
- 课程 Schema 强制 5 个卡组，每组至少 12 张；F 卡必须存在有效 `sourceIds`。
- 饿了么内置课件必须包含 `e08-c-05`、`e08-f-02`、`e08-r-04`。
- 卡牌全文搜索、F／R／G／U 筛选和直接跳转具备浏览器测试。
- 学员预览与 `seat.js` 对同一卡 ID 输出一致。
- 隔离 Alpha Run 跑通“搜索→修改→保存→刷新→八席验证→恢复旧快照为新 revision→再次刷新”；生产登录态完成搜索、预览、手牌与版本只读核验。
- 桌面和移动端均能完成卡牌查找、编辑与预览。
- 缺少 `decks`、卡数不足、来源失效或版本不一致时禁止发布。

## 非目标

- 不继续扩展 `/workshop/` 的课程共识功能。
- 不合并工坊 JSON 与 Alpha 运行课件 JSON。
- 不把每次随机产生的卡牌序号和未读状态写死进课程 JSON。
- 不因为编辑器改进而取消 Alpha 的人工刷新确认。
- 不让正式课堂自动加载未经发布和验收的草稿。
