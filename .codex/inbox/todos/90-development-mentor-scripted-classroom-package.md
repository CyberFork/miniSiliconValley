# 为开发导师“立棍”PPT制作剧本杀组课件与课堂编排

## 一、任务定位

围绕 T-089 的 D／开发导师 HTML-PPT，制作一套可以在真实 Classroom 中运行的剧本杀组课件。它不是另一份 PPT，也不是把每一页幻灯片改造成一个系统 Block，而是把“立棍、分层开发、测试与纠偏”转换为学生可以亲自经历的课堂模拟。

真实开发顺序放在 T-091 和 T-089 之后：先让 P 导师的饿了么剧本和产品成果归位，再冻结 D 导师 PPT，最后制作与 D PPT 匹配的剧本组课件。

推荐的课堂事件：

> **校园共享设备预约系统失控事件**

剧情外壳是工程事故调查，教学内核是复杂任务治理。学生需要根据不完整的私密证据，找出系统为什么失控，建立一级主棍，拆分子棍和微棍，写出验收标准，并在新异常出现后完成纠偏。

## 二、与其他任务的边界

```text
T-089
负责D导师PPT本体、课堂文案、立棍母图和浏览器播放体验

T-090（本任务）
负责D导师剧本、私密卡、公共事件、学生提交、导师验收和中控时序

T-091
负责将既有饿了么历史内容收敛到P导师PPT与产品剧本包
```

本任务不得把饿了么史实卡重新包装为 D 导师技术课，也不得编造饿了么的接口、日志或自动化测试历史。

## 三、课堂共同交付物

剧本组课件最终帮助每个学生团队完成一张可保存、可审核的 `DevelopmentStick／开发立棍卡`：

1. 当前情况与真实问题。
2. 用户和主要任务。
3. 一级主棍目标。
4. 最小完整用户路径。
5. 最终验收标准。
6. 约束、禁止事项和红线。
7. 2～3 根二级子棍。
8. 至少一根三级微棍。
9. 至少一个可以执行或人工判断的测试。
10. 突发偏差、修改理由和纠偏记录。

## 四、PPT、学生端、D导师和DM中控的职责

### 公共PPT

- 发布所有学生共同看到的剧情背景和公共事件。
- 解释立棍母图、开发方法和测试方法。
- 显示公共倒计时、阶段目标和最终复盘。
- 不显示任何学生私密卡，不直接修改 Classroom 状态。

### 学生端

- 接收和阅读自己的私密线索。
- 区分事实、猜测和未知。
- 将允许公开的证据提交到团队证据区。
- 参与填写开发立棍卡、子棍和测试。
- 查看团队提交状态和导师退回原因。
- 使用 Pad 触摸即可完成，不依赖 hover、键盘快捷键或长篇文本输入。

### D导师端

- 查看学生是否已阅读线索，以及团队当前公开的证据。
- 只做观察、提问、验收和专业讲解，不提前公布答案。
- 验收一级主棍是否清楚，子棍是否仍与主棍对齐。
- 在卡片或当前 Block 中打开绑定的 D 导师课件。
- 可以退回团队提交，并写明需要补充的字段。

### Admin DM中控

- 开始事故、分发卡片、推进阶段和发布突发事件。
- 暂停、后退、刷新和恢复当前课堂状态。
- 控制公共投屏进入相应教学章节。
- 使用 Classroom 作为唯一运行状态真值；PPT只提供讲解和提示。

## 五、一个事故、四个剧情检查点

PPT内部约18页，但 Classroom 只建立少量稳定的剧情检查点，避免 Slide 与 Block 一对一耦合。

### 检查点A：系统失控

公共事件：校园共享设备预约系统试运行失败。

学生任务：

- 阅读私密卡。
- 提交一条可观察事实。
- 提交一个初步判断。
- 指出一项仍不知道的信息。

### 检查点B：建立主棍

团队填写：

```text
当前情况
用户及主要任务
一级目标
完成标准
约束与禁止事项
```

D导师验收后才能进入下一阶段；只写“做一个预约系统”不得通过。

### 检查点C：分解与测试

团队拆分：

- 查看空闲时段。
- 创建预约。
- 判断预约冲突。
- 取消预约。
- 显示并保存最终结果。

每根子棍必须带有验收标准，并为其中至少一根子棍补充测试。

### 检查点D：突发事件与纠偏

系统发布新的异常证据，例如：

- 页面显示成功，但服务器没有保存记录。
- 两名学生同时预约了同一台设备。
- 断网恢复后重复提交。
- 学生退出后，下一位使用者仍能看到上一人的预约信息。

团队需要判断哪根棍失败、现有测试为什么没有发现、需要补充什么验收标准，以及是否需要向上修改主棍。

## 六、40～50分钟运行节奏

```text
00～05分钟   PPT发布事故，学生进入剧情
05～10分钟   系统分发私密线索，学生整理事实、猜测和未知
10～20分钟   D导师讲解复杂度淹没、完整立棍和三级分层
20～30分钟   团队建立一级主棍和端到端主干
30～38分钟   团队拆分子棍并写验收标准
38～43分钟   DM发布突发事件，团队定位偏差并修改方案
43～48分钟   团队提交开发立棍卡，D导师完成验收
48～50分钟   PPT显示通关检查并复盘
```

真实课堂可以在阶段内微调，但不得因为剧本内容过多而挤占团队实践和最终验收。

## 七、私密卡池设计

第一版建议准备约12张短卡，按照证据类型组成卡池，而不是绑定固定四名学生：

```text
用户现场线索       3张
系统与数据线索     3张
业务规则线索       2张
测试记录线索       2张
边界与未知线索     2张
```

示例方向：

- 学生看到“预约成功”，设备管理员的名单里却没有记录。
- 两次请求相隔很短，两次都通过“时段可用”检查。
- 学校规定同一时间只能预约一台设备，但开发任务没有写入这条规则。
- 自动化测试只检查成功提示，没有检查数据库记录。
- 页面要求填写与预约无关的家庭住址和家长手机号。
- 尚不知道断网重连后会不会重复提交。

每张卡只承载一个主要信息，并附带一个行动要求：说出证据、指出未知、判断影响哪根棍，或提出一项验收标准。

### 来源边界

- 本事故是课堂模拟，卡片必须沿用现有内容边界明确标记为 `R／课堂模拟`。
- 不得把模拟日志、模拟用户或模拟测试写成来源支持的历史事实。
- 如果使用真实软件事故作为补充资料，必须保留来源并与模拟剧情分开显示。

## 八、适配可变学生人数

不得把卡片和任务写死为4名学生，也不得把PDMO当成学生分工。

- 2名学生：每人获得多张不同类型的线索。
- 4名学生：每人约2～3张。
- 6名学生：每人约1～2张，并增加观察或质疑任务。
- 更多成员：允许多人共享一种视角，但各自仍需完成阅读或判断动作。

分配策略根据当前 Classroom Membership 计算；同一团队必须通过交流才能拼出完整证据链。

## 九、PDMO边界

- P、D、M、O是导师专业分工，不是学生身份。
- 学生获得的是用户现场、系统日志、业务规则、测试记录等临时证据视角。
- D导师负责本课堂的专业引导，但 Admin DM 权限仍可由符合权限规则的账号承担。
- 五个课程步骤是团队项目进度，不能与PDMO导师角色做一对一绑定。

## 十、建议的数据对象

剧本组课件应作为版本化内容进入统一课程工厂，而不是硬编码在某个页面：

```text

  scriptId
  mentorRole: D
  caseId: device-booking-incident
  coursewareRevision
  duration
  checkpoints[]
  cardPool[]

```

字段名可根据现有数据模型调整，但必须保留课件版本、剧本版本、具体 Classroom 和学生提交之间的可追溯绑定。

## 十一、实现步骤

1. 以 T-089 确认后的18页故事板为内容基线。
2. 审计现有剧本引擎、私密卡、团队公开、导师验收和DM推进能力。
3. 编写事故剧情、四个检查点和12张左右的卡片初稿。
4. 定义开发立棍卡的提交结构和导师验收规则。
5. 将剧本作为独立 `ScriptPackage` 版本化，不硬编码进 PPT。
6. 绑定 D 导师 `CoursewarePackage` 的确定 revision，只绑定章节／检查点，不绑定每一页。
7. 在 Studio Preview 中平铺验收学生、D导师、公共投屏和中控视图。
8. 在 Test Classroom 中以2人、4人和6人团队分别跑完整流程。
9. 使用 iPad／平板完成学生端触摸、输入、横竖屏和断网恢复验收。
10. 通过后随课程 release 一起进入 Production Classroom。

剧本内容可以在 T-092 部署期间并行编写，但最终 Classroom 绑定和发布验收必须等待 T-092 产生可访问的确定 courseware revision。

## 十二、验收标准

### 教学与剧情

- [x] 一个工程事故贯穿课堂，不使用多个无关故事分散注意力。
- [x] 剧情的根本问题是目标、边界、验收和反馈缺失，而不是寻找唯一“坏人”。
- [x] 学生必须组合不同证据才能形成合理判断。
- [x] 私密卡信息短、可行动，不是大段背景阅读。
- [x] 突发事件能够迫使团队检查测试和完成一次真实纠偏。
- [x] 学生最终形成可保存、可审核的开发立棍卡。

### 系统边界

- [x] PPT、学生端、D导师端和DM中控职责没有重复或冲突。
- [x] PPT不直接修改课堂状态，Classroom仍是运行状态真值。
- [x] 只使用少量剧情检查点，不建立Slide与Block的一对一脆弱绑定。
- [x] 剧本、课件和Classroom分别绑定确定revision并可追溯。
- [x] 饿了么历史内容没有混入D导师模拟事故。
- [x] PDMO没有被重新解释为学生分工。

### 多人数与Pad

- [x] 2人、4人和6人团队均能合理分配线索并完成任务。
- [x] 学生只使用触摸和软键盘即可完成核心流程。
- [x] 私密卡不会泄露给其他学生，切换账号后不会残留。
- [x] 断网、重复提交、导师退回和课堂后退均有明确恢复行为。

## 十三、非目标

- 不重写 D 导师 PPT 本体；该工作属于 T-089。
- 不迁移或整理饿了么内容；该工作属于 T-091。
- 不把每一张幻灯片实现成一个 Classroom Block。
- 不把剧本杀理解为寻找凶手或给某个学生角色定责。
- 不在本任务中重新设计整个课程工厂、账号系统或发布状态机。
