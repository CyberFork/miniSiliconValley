# 修复课堂创建表单空选项、无反馈禁用及验收引导

> 补充反馈见 [T-111](111-test-classroom-create-version-and-lifecycle-management.md)：r9 旧测试课存在时仍须显眼地提供创建 r12 新 TEST 的入口；初始化依赖失败不能让创建区消失。课程/账号加载与前置验收提示需和该任务衔接。

## 用户反馈

> 这些无法填入，并且最后创建真实 UI 验收课堂 → 无法点击也没有提示。

截图为 TEST Classroom Factory：课程 exact 版本与学员人数下拉框为空，底部创建按钮无法点击。课程下方已有一行「没有可创建的版本：请先到多角色视图验收」，但不在最终操作按钮附近，没有下一步链接，也未解释具体是哪门课缺少什么条件。

## 本轮原因核对

源码：`app/classroom/ClassroomHub.tsx`。

1. `FactoryPanel` 的 `eligible`（约165–170行）过滤掉没有有效 exact View 回执的课程；TEST只保留当前Candidate/Released，PRODUCTION还要有效UI回执及Released。
2. 课程下拉框（约300行）只渲染eligible，没有空态option；列表为空时仍呈现一个像可操作输入框的空select。
3. 人数下拉框（约303行）仅从选中课程learnerPolicy生成options；没有course时也为空。
4. 创建按钮（约309行）因缺course/viewReceipt等设置原生disabled；`createClassroom`里的缺条件报错（约220行）无法通过点击触发。
5. 其他表单校验通过父级onError显示在课堂中心顶部，长页面下用户可能看不到反馈。
6. `course = ... ?? eligible[0]`可能在指定课程不可用时静默回退到另一课程，应检查深链失效/版本替换场景，避免用户以为仍在创建原课程。
7. 加载逻辑主要在页面初始化执行；从另一页完成人工验收再回到既有标签后，是否重新获取回执需要覆盖。

截图与源码可确认「当前页面没有合格课程可选→人数为空→按钮禁用」这条链。**尚未读取该用户线上bootstrap，不能断言一定是用户没验收**：还可能没有课程、回执因版本/构建变化失效、权限过滤或数据加载异常，必须在实现中分别说明。

## 修复目标

用户无需理解ViewAcceptanceReceipt等内部名称，就能知道：

- 我准备创建哪门课的哪个版本？
- 当前能填什么？什么被锁定，为什么？
- 还差哪项条件，在哪里补齐？
- 补齐以后怎样继续，不丢已填配置？

保留「先验收视图→创建TEST→真实UI验收→发布→正式课堂」服务端门槛，不删除门禁，不代签人工回执。

## 实现方案

### 1. 明确空态与不可用原因

- 区分加载中、网络失败、无权限、没有课程、已有课程未验收、回执失效、课件未就绪等状态；网络错误不能显示为没有课程。
- 展示有权查看课程的名称、courseDataId/版本和准备状态，不只把所有不合格版本过滤到消失。
- 建议允许选择待验收课程查看原因、准备表单；只有最终创建受门禁限制。选择不等于绕过验收。
- 没有任何课程时显示明确占位项，并提供「去课程编辑器保存课程」。
- 有课程但尚未通过视图验收时提供「前往多角色视图验收」，携带对应courseId/revision/digest；具体失效原因使用服务端结果，不硬编码猜测。

### 2. 字段联动符合用户直觉

- 有选中课程后按其真实learnerPolicy列出人数，不写死4人，也不显示没有选项的假输入框。
- 暂无可用课程时人数明确禁用并标注「请先选择课程」，而不是白色空下拉。
- 导师创建课堂时初始Admin DM锁定本人属于既定规则；显示锁定原因及后续授权入口，不让用户误以为表单坏了。
- 课程/环境切换时逐项校验原有配置，保留仍合法的课堂名、人数和账号选择；不能静默换另一门课或丢配置。
- 无法确定有效人数时，不让「一键生成4＋4账号」暗示人数已经正确配置；独立账号准备需明确数量，不能靠反复生成账号解决课程未验收。

### 3. 操作区始终有可执行的下一步

- 创建按钮附近持续显示就绪清单：课程视图验收、导师/学员账号、人数、四套课件；PRODUCTION再增加UI回执/已发布条件。
- 每项未就绪原因有对应动作：去验收、去补课件、去配置成员、刷新状态等。
- 可以保留原生disabled的「创建」按钮，但旁边必须有能点击的「查看原因/完成前置条件」；不能把提示只放在disabled按钮的click处理里。
- 任何字段/服务端校验失败都显示在字段旁或创建区域，自动定位首个问题，支持键盘与触摸；不只在页面顶部或hover tooltip给提示。
- 用户主文案使用「先完成课程视图检查」「还缺2位学员账号」等易懂表达；exact、事务、回执对象名放详情中。

### 4. 补齐条件后能继续

- 返回页面/重新获得焦点时安全刷新门禁，或提供显式刷新按钮；刷新失败不清除已填内容。
- 当前选定版本失效时明确说明并让用户选择处理，不自动跳到eligible[0]。
- 创建前服务端再次校验同一exact版本；检查与提交之间发生变化时明确返回原因，无半个课堂、重复创建或错误成功提示。
- 保留安全的返回地址和非敏感表单上下文；账号凭据和会话信息不能进入URL。

## 验收矩阵

- [ ] 首次进入无课程：有空态说明和编辑器入口，人数不是空白可操作框。
- [ ] 有Candidate无View回执：显示该课程与未验收原因，可一键前往其exact视图验收。
- [ ] 曾通过但回执失效：显示具体原因，不能一概写「未验收」。
- [ ] 完成验收后返回/刷新：正确回填课程，显示其支持人数范围，保留合法配置。
- [ ] 指定深链版本不合格但其他版本合格：不静默改成另一门课。
- [ ] 人数2/4/6、重复账号、缺导师/学员、课件缺失/版本不匹配均在操作区给出具体修复入口。
- [ ] Admin DM被规则锁定时有说明，不被误报为输入失败。
- [ ] TEST与PRODUCTION门槛分别正确，UI引导不放宽服务端限制。
- [ ] 长页滚动到底部仍能看见不能创建的原因；手机/Pad不依赖hover，键盘可访问下一步。
- [ ] 网络失败、401/403、409、提交中和重复点击有明确反馈；不留下半个课堂或重复账号。
- [ ] 不伪造人工验收，使用本地合成数据测试，不在生产创建测试账号/课堂作为本轮调研手段。

本轮只调研与建单，尚未修复、部署或修改线上回执。T-102负责验收契约本身，本任务负责把真实门禁状态清楚地呈现为可完成的用户流程。
