# 补齐课程待核对和家长 QA 缺口的人工审核闭环

## 保留用户边界

未覆盖内容只能记录，由DM/导师补充、审核再入库。模型不自行编造事实、不自行关闭缺口、不把待审核清单直接并入可检索知识。

## 两类对象不要混淆

- **课程内容待核对**：CourseDefinition.contentPackages.reviewQueue，如P课件来源/版本差异。
- **家长问答待补充**：knowledge-gaps.ndjson，由家长问题触发；不是课程编辑todo本身。

可以同一内部工作台提供两个入口，但不可混成一份课程真值或用模型答案互相回填。

## 审计依据

- T-095 Candidate仍有2个open：P本地快照与runtime来源不一致、P第21页“2008 App”来源风险。现行内容已建议跳过该页，不能据此宣称整份P课件已经全部人工核对。
- course-package.ts:756–770只校验reviewQueue格式；StudioApp/releases与editor未提供专门审核清单。并非要求所有open强制阻止发布，而是当前缺少可见、可确认的处置。
- knowledge-gap-store.ts:44–57对每次观察都生成pending_dm_review；同ID之前resolved_already_covered后再次观察仍pending。按PARENT_QA.md提供的最后事件汇总方式会“重新打开”。probe已验证事件行为，是否应重开属于待确认产品规则。
- QA健康页只证明记录功能配置启用；写盘失败目前仅日志提示。没有针对磁盘失败的团队可见处理回执。
- app/data/parent-qa-knowledge.ts是静态人工编目内容，发布与课程更新不是自动同一事务；应避免已回答问题因旧摘要又成缺口。

## 实现建议

1. 课程审核清单按位置、类别、影响、建议动作展示；负责人选择修订/补来源/本次显式排除。签署者、时间、exact版本记录清楚。
2. 区分阻断与非阻断项；例如明确排除的P第21页不默认为已修复，也不能被“全部通过”隐藏。
3. QA事件区分observation/review/reopen；新增观察只增加次数/最后时间，不无条件覆盖人工resolution。
4. 是否重开已解决问题必须基于人工决策或版本/问题变化证据，展示原因；不要仅靠相同模型再次返回knowledgeGap就自动推翻人工结论。
5. 录入补充资料保留来源/审核者/版本，审核通过后经过测试发布进入知识；解决清单与知识版本建立可追溯关联。
6. 缺口落盘失败可见地告警和重试，保留“未记录成功”状态；不把失败内容打印进公共日志。
7. 记录与展示均脱敏，不留API Key、对话全文或儿童身份信息；历史会话已出现的凭据建议另行轮换，记录中不复制密钥。

## 验收

- [ ] 相同问题多次出现正确累计，已有人工解决状态按批准规则保留/重开。
- [ ] “已覆盖”“新增知识解决”“范围外”三种处置可区分和追溯。
- [ ] 模型不能修改审核状态，pending内容永不被检索器自动读取。
- [ ] DM/导师能看到课程open项及其明确处理，而非只能打开JSON。
- [ ] 写盘失败不给用户虚假的“已记录”，内部能发现故障。
- [ ] 审核与入库测试全部使用合成/脱敏数据，不调用真实儿童资料或付费模型。
